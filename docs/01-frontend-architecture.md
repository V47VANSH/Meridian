# Frontend Architecture

Owner: Person A · Parent doc: [00 — Architecture Overview](00-architecture-overview.md)

## 1. Stack

- **React 18 + TypeScript**, bundled with Vite
- **PWA**: `vite-plugin-pwa`, installable, offline app-shell, service worker for push notifications
- **Styling**: Tailwind CSS
- **Server state**: TanStack Query (React Query) — matches the REST contract, handles caching/invalidation for live data (e.g. booking slot availability)
- **Client/UI state**: Zustand (auth session, UI toggles) — deliberately not Redux; state surface here is small
- **Realtime**: `socket.io-client`
- **Routing**: React Router, route-based code splitting per role dashboard

## 2. Folder Structure

```
frontend/
  src/
    app/                # app shell, providers, router
    api/                # generated typed client (from OpenAPI) + query hooks
    features/
      auth/
      maintenance/
      complaints/
      bookings/
      visitors/         # guest pass + SOS
      announcements/
      dashboard/
    components/         # shared, dumb UI components
    hooks/              # shared hooks (useSocket, useAuth, etc.)
    lib/                # utils, constants
    styles/
  public/
    manifest.json
    service-worker.ts
```

Each `features/<epic>` folder owns its pages, its feature-local components, and its API query hooks — mirrors the backend's module boundaries so a person reading one feature folder doesn't need to hop across the codebase to understand it.

## 3. API Client

Backend publishes an OpenAPI spec (auto-generated by NestJS Swagger decorators). Frontend runs `openapi-typescript-codegen` (or `orval`) against that spec to generate a typed client + React Query hooks into `src/api/generated/`.

**Why this matters for the team**: ownership is horizontal (Person A = all frontend, Person B = all backend). Without a contract, A is blocked waiting for B to finish routes. With OpenAPI-first, B publishes the contract early (even before every route is implemented — NestJS can serve the spec from decorated-but-stubbed controllers), A codegens against it and starts building UI against a mock server (e.g. `msw`) using that same contract, and both converge as B fills in real logic.

## 4. Role-Based Routing

One SPA, gated by role — not separate builds per role:

```
/                     → redirect based on role
/login, /register
/resident/*           → RESIDENT_OWNER dashboard, payments, complaints, bookings, guest passes, SOS
/official/*           → SOCIETY_OFFICIAL dashboard, resident mgmt, complaint triage, booking schedule, announcements
/non-resident/*        → NON_RESIDENT_OWNER read-mostly views + guest pass generation
/guard/*               → SECURITY_GUARD guest-pass verification, SOS inbox
/staff/*               → MAINTENANCE_STAFF / CLEANING_STAFF assigned task views
/admin/*               → SUPER_ADMIN society onboarding (platform-level, separate from society roles)
```

A route guard reads role + tenant from the decoded JWT (via the auth store) and redirects unauthorized access before the page even mounts.

## 5. Key Pages Per Epic

| Epic | Pages |
|---|---|
| Maintenance | Invoice list, Pay Now (Razorpay Checkout embed), payment history, (official) invoice management |
| Complaints | Raise complaint form, complaint list + status timeline, (official/staff) triage queue sorted by ML-assigned urgency |
| Booking | Facility calendar (slot grid), my bookings, (official) schedule management |
| Visitor/SOS | Generate guest pass (shows QR), guest pass history, SOS button (resident), SOS inbox (guard) |
| Announcements | Announcement feed, (official) composer |
| Dashboard | Resident: payments + complaints + bookings summary in one view (Story 5.1). Official: centralized records view (Story 5.2) |

## 6. Realtime Integration

On login, the client opens a Socket.IO connection and joins `tenant:{id}:user:{id}` and `tenant:{id}:role:{role}` rooms (server-assigned, client can't spoof room membership — see [02 — Backend Architecture](02-backend-architecture.md#9-realtime-gateway)). Listens for:

- `sos.raised` (guards only) → toast + inbox update + sound
- `sos.acknowledged` (raiser only) → status update
- `complaint.status_changed` → live status timeline update
- `booking.slot_taken` → live-disables that slot in the calendar grid for everyone viewing it

## 7. PWA / Push Notifications

- `manifest.json` for installability ("Add to Home Screen")
- Service worker registers for Web Push (VAPID public key from backend config)
- On permission grant, subscription is POSTed to backend and stored against the user — backend's notification dispatcher (see [02](02-backend-architecture.md#10-notifications)) pushes to it

## 8. Testing

- **Component/unit**: Vitest + React Testing Library, colocated with features
- **E2E**: Playwright — golden paths: login, pay invoice, raise complaint, book facility, generate guest pass, raise SOS (one spec per epic, run in CI against a seeded staging-like environment)
- **Contract**: generated API client is regenerated in CI from the current OpenAPI spec; a diff failure signals the frontend is out of sync with backend
