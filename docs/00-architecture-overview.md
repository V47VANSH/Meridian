## 1. Objective (from Milestone 1)

Streamline apartment society operations through a centralized platform for maintenance payments, complaint management, facility booking, visitor management, emergency assistance, and society communication — improving transparency, accountability, and operational efficiency for residents and society officials.

## 2. Product Decision: Multi-Tenant SaaS

Rather than building for a single apartment complex, the platform is architected as **multi-tenant SaaS**: one deployment serves many societies, each fully isolated by `tenant_id`. This is a deliberate scope expansion beyond the literal Milestone 1 ask, chosen because:

- It's a stronger architecture/engineering story (tenant isolation, row-level security, platform-level admin) without meaningfully increasing feature-build time.
- It's still trivially demoable with 1–2 seed societies.
- It maps cleanly onto real-world PropTech SaaS products (industry-standard shape).

```
Platform (SuperAdmin)
  └── Society A (tenant_id = 1)
        ├── Society Officials
        ├── Resident / Flat Owners
        ├── Non-resident Flat Owners
        ├── Security Guards
        ├── Maintenance / Cleaning Staff
        └── Service Providers
  └── Society B (tenant_id = 2)
        └── ... (fully isolated from Society A)
```

Every tenant-scoped database table carries a `tenant_id` column. The scope for a request comes from a `get_tenant_id` dependency that reads the authenticated JWT's claims — never a request body or query parameter — and every tenant-scoped query filters on it. A dedicated test suite attempts each cross-society access path with a token from another society, so the guarantee is enforced by tests rather than by convention (see [03 — Database Architecture](03-database-architecture.md#4-tenant-isolation)).

## 3. Users & Roles

| Tier | Role | Core capabilities |
|---|---|---|
| Primary | `RESIDENT_OWNER` | Pay maintenance, raise complaints, book facilities, generate guest passes, SOS, view dashboard |
| Primary | `SOCIETY_OFFICIAL` | Manage residents, payments, complaints, bookings, announcements |
| Secondary | `NON_RESIDENT_OWNER` | View announcements, track payments/complaints remotely, generate guest passes |
| Secondary | Visitor / Guest | Holds a digital guest pass (not a full account — see below) |
| Tertiary | `SECURITY_GUARD` | Verify guest passes, receive & acknowledge SOS alerts |
| Tertiary | `CLEANING_STAFF` | Receive assigned cleaning tasks |
| Tertiary | `MAINTENANCE_STAFF` | Receive & resolve assigned complaints |
| Tertiary | `SERVICE_PROVIDER` | Fulfil maintenance service requests |
| Platform | `SUPER_ADMIN` | Onboard/manage societies (platform operator, not a society member) |

Visitors are **not** full user accounts — they hold a signed, time-boxed, single-use guest-pass token generated by a resident. This keeps the auth model simple (no visitor registration/login flow) while still giving guards something cryptographically verifiable to scan.

## 5. Technology Stack Summary

The **Status** column records what is actually in the repository as of the final
submission, so this table can be read as a delivery record rather than an
intention. "Designed, not built" items are deliberate scope decisions, not
oversights — each is argued in the final report's *Design evolution and
deviations* section, and the system is built so that every one of them degrades
to a working fallback rather than a broken feature.

| Layer | Choice | Status | Why |
|---|---|---|---|
| Frontend | React + TypeScript (Vite) | **Implemented** | One codebase, no app-store overhead |
| — PWA (installable, offline shell, push) | `vite-plugin-pwa`, service worker | Designed, not built | Deferred; the app is delivered as a standard SPA |
| Backend | FastAPI (Python 3.11), modular monolith | **Implemented** | One router per epic keeps a consistent pattern for a 5-person team; same language as the ML service, so the stack is uniform rather than split |
| ORM | SQLAlchemy 2.0 + Alembic | **Implemented** | Typed models and versioned migrations |
| Database | SQLite (default) / PostgreSQL via `DATABASE_URL` | **Implemented** | SQLite so the project clones and runs with no server; the Postgres path is exercised in CI |
| — Supabase Postgres | Managed Postgres | **Implemented** | The deployed database; migrations applied by Alembic before the server starts |
| — Supabase Storage | Object storage | Not built | Complaint photo upload therefore has nowhere to put a file and is not implemented |
| Cache/Queue | Redis (Upstash) | **Implemented** (optional) | Backs the booking lock and the rate limiter. Both fall back to in-process equivalents when unset — correct for one instance, insufficient for several |
| ML | FastAPI (Python), separate service | **Implemented** | Python is the right tool for ML; kept as its own deploy since one teammate owns it end-to-end |
| Payments | Razorpay, test/sandbox mode | **Implemented** (server side) | HMAC signature verification is real; completing a checkout needs live gateway credentials |
| Realtime | FastAPI WebSockets + Redis pub/sub | Designed, not built | Clients poll instead; every REST endpoint behind the intended events exists and is tested |
| Notifications — in-app feed | `Notification` rows + polled feed | **Implemented** | The in-app row is always written, whatever happens to external channels |
| Notifications — Web Push / SendGrid / Twilio | External delivery | Designed, not built | Channel routing is implemented and logged at the dispatch boundary; delivery needs provider credentials |
| CI/CD | GitHub Actions | **Implemented** (CI) | Lint, typecheck, test and contract-drift checks on every PR; no deploy step, as nothing is hosted |
| Hosting | Vercel (frontend) + Render (backend + ML) | **Implemented** | Deployed; the frontend proxies `/api` to Render so the browser stays same-origin |
| Monitoring | Sentry + UptimeRobot | Designed, not built | `/health` liveness endpoints exist on both services; no error-tracking SDK is wired in |

## 7. Cross-Cutting Concerns

- **Security**: JWT access (15 min) + rotating refresh tokens (stored hashed); role and tenant guards as dependencies on every route, with the society scope read from the token claim and never from the request. Fixed-window rate limiting, tighter on auth and SOS endpoints than on general traffic. Full detail in [02 — Backend Architecture](02-backend-architecture.md#4-security).
- **Notifications**: the in-app row is always written regardless of what happens to any external channel. Channel routing is implemented and logged at the dispatch boundary; queued external delivery (so a flaky SMS/email provider never blocks a request) is designed but **not built**. Full detail in [02 — Backend Architecture](02-backend-architecture.md#10-notifications).
- **Auditability**: every state-changing action (payment, complaint status change, booking, guest pass, SOS) writes an `AuditLog` row — directly satisfies the Milestone 1 goal of "transparency and accountability."
- **ML fallback**: both ML endpoints have a deterministic fallback (rule-based category guess / neutral risk score) if the ML service is unreachable or returns low confidence — the platform must keep functioning even if ML is down. Detail in [04 — ML Architecture](04-ml-architecture.md#7-fallback-behavior).

## 8. Build Phasing

Since timeline isn't fixed yet, the design is meant to be built in phases rather than all-at-once:

1. **Phase 1 (MVP)**: Auth + multi-tenancy skeleton, Maintenance (manual payment marking, no gateway yet), Complaints (manual triage, no ML yet), basic Booking. Gets a thin vertical slice working end-to-end across all 5 layers early.
2. **Phase 2 (Full feature set)**: Razorpay integration, both ML services live, Visitor/SOS, Announcements, real-time layer, full notification channels.
3. **Phase 3 (Polish)**: CI/CD hardening, monitoring/alerting, test coverage push, PWA polish, accessibility pass, ML model iteration (e.g. transformer-based complaint classifier as a stretch goal).
